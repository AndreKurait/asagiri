# Private registry certificate authorities

`daemon.json` accepts `registry-ca-certificates`, an object mapping an exact registry authority to a PEM certificate bundle. For example, `{"registry-ca-certificates":{"registry.example":"-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n"}}`. Supply actual CA certificates; placeholder text is rejected. Certificates are public trust material, not private keys. Never include private keys.

The engine selects roots for each actual TLS destination. Only HTTPS connections to that authority use the selected roots. Other engine destinations, including redirects and token services, retain the default public roots unless separately configured. Hostname, chain and expiry verification remain enabled. A missing port means HTTPS port 443; explicit 443 is equivalent. Other ports are distinct. Wildcards, URLs and CIDRs are rejected. A custom-CA authority cannot also be an insecure registry.

The complete certificate bytes form part of the registry policy and connection-pool identity. BuildKit receives the same policy snapshot and content-addressed certificate files through its native per-registry `ca` setting. Changed CA policy is rejected before persistence while builds are active. An idle builder is stopped before saving changed trust; failed configuration copies remain pending and must succeed before another build is admitted. An already-running builder after daemon restart is also refreshed before admission. No system trust store or environment override is required. The setting is bounded to 16 authorities, 48 KiB total PEM and 32 certificates per authority, within the existing 64 KiB daemon configuration limit.

This governs engine and BuildKit registry clients. An external SDK's control API TLS trust remains that SDK's responsibility. Trusting a CA does not configure registry credentials, DNS, routing or an HTTP fallback.
